作品内容摘要：

工业园区边缘通信需要兼顾国密算法选型、长期数据保密与存量设备渐进迁移。传统公钥机制面临未来量子密码分析的风险，而整体替换设备又受到运行连续性、接口及资源条件制约。通信保护还必须区分报文写出、对端接收与业务处理，避免仅凭发送成功判断控制操作已经完成。

针对 A1-31 赛题，本作品设计并实现 EdgeHybrid 软件原型，以 SM2 与 ML-KEM-768 混合四步握手建立双分支共享材料。采用 HMAC-SM3 实例化 HKDF，本文简称 HKDF-SM3。结合 T2/T4 分阶段转录派生确认与应用密钥，并通过 SM4-GCM 保护双向记录。可信配置允许传统模式与混合模式共存，混合失败不静默回退。

作品的技术工作集中在三个层次：以 T2/T4 分阶段转录将身份、协商参数与两分支建钥材料绑定；用严格记录序号和匹配 ACK 连接通信保护与业务处理；通过运行编号、源码清单、程序身份和原始日志组织可复现实验。本机 Web 工作台将这些机制转化为设备连接、温度上报、间隔控制和证据导出操作。

在 Windows 本机 TCP 环境下，同生产源码的 QPC 测试宿主完成混合模式 1,000/1,000 次正式握手，客户端完整握手调用观察区间的平均耗时为 1.1479 ms，P95 为 1.4731 ms，长期身份初始化与 TCP 建连位于计时区间之外。已建通道的 Suite 2 控制请求—ACK RTT P95 为 0.2645 ms；4,096 B 载荷的 SM4-GCM 加密／解密吞吐约为 605.92／650.78 MB/s。握手、业务与原语分别计量，原始样本、环境和复算脚本共同构成数据依据。

本作品采用“国密身份认证＋混合建钥”的渐进迁移路径：SM2 承载身份认证，ML-KEM-768 提供后量子建钥分支。验证包括 Windows 软件原型、模拟设备，以及 Android ARM64 手机的跨设备温度上报与控制功能；本文正式性能统计仍来自 Windows 本机批次。协议组合安全分析、后量子签名认证及目标工业硬件适配是后续研究和工程验证方向。

1.作品功能与性能说明

1.1 研发问题与威胁模型

1.1.1 工业边缘迁移要解决的问题

本作品面向园区边缘设备与网关之间的遥测和控制通信。设计目标是在保留国密算法选型和显式兼容策略的同时，引入后量子建钥分支，并使操作结果能够由通信与业务证据共同核对。当前软件实现对应模拟温度、采样间隔及身份维护，并以手机电池温度和手电筒补充实机验证；工业现场设备接口仍需单独适配。

  • 迁移与资源：不同设备的运行周期、接口和资源条件不同；传统身份通过可信配置保留，混合模式优先，失败不静默回退。
  • 长期保密：攻击者可保存当前握手与密文，未来再尝试解密；建钥分支与在线身份认证需要分别分析。
  • 业务可信：写入 socket 不等于操作完成。遥测由网关验收，控制由设备返回实际生效状态，再由网关核验。

1.1.2 HNDL 与 Mosca 迁移风险框架

Shor 算法揭示传统整数分解与离散对数机制在相应量子计算模型下的风险；HNDL 则关注历史密文被保存后回溯解密的情形。[1][2]

令 X 为数据仍需保密的时间，Y 为完成迁移所需时间，Z 为具备相关密码分析能力的量子计算机出现前的估计时间。Mosca 框架以 X + Y > Z 提示提前迁移的必要性；各量必须结合资产、工程安排与假设评估，而不是本作品给出的固定时间预测。[2]

1.2 核心技术贡献与设计原则

作品围绕混合握手、业务因果确认和可复现验证三项贡献展开。协议设计解决身份、协商与建钥材料的绑定；业务层解决“已经写出”和“确已处理”的区分；验证层将每项结论关联到源码、程序和原始记录。工作台、设备池与批量操作为三者提供统一入口。

1.2.1 混合建钥与渐进密码迁移

Suite 2 采用 SM2 密钥交换与 ML-KEM-768 的共享结果，Suite 1 提供可信配置允许的传统模式。团队聚焦于四消息混合握手、模式策略、身份约束及失败状态机的设计与实现；底层原语分别调用 Go 标准库和 gmsm 的相应接口，参数及来源见表2.2和表2.7。

1.2.2 T2/T4 分阶段转录绑定与协商完整性

前两条消息形成 T2，用于展开两个方向的 Finished 密钥；四条完整消息形成 T4，用于展开应用方向密钥、Nonce 前缀和 SessionID。身份签名、SM2 确认和 Finished 共同保护协商内容，各输入均不包含自身输出。精确流程及密钥材料见 §2.1.6—2.1.7。

1.2.3 安全记录与业务因果确认

written ≠ confirmed

严格 Seq 与 SM4-GCM 保证所接纳记录通过会话、方向、顺序和认证检查；四态操作进一步回答“本次业务是否得到相应确认”。遥测 confirmed 是网关验密和业务校验后的接收观测，控制 confirmed 则要求设备实际处理后返回匹配 ACK。

1.2.4 可复现实验与证据追踪

以运行编号、源码清单、构建身份、会话和操作标识串联原始日志，形成可复算的实验材料。指标主表统一摘要、结果章节和总结中的数值，保留计算公式与原始文件入口。各性能批次保持原有版本身份，界面修订与新构建另立验证记录。

外层 Length 为其后字节数，不含 4 B 长度自身。受保护记录固定开销为 2 + 33 + 16 = 51 B，其中 2 B 为 wire 版本／类型；若计入长度字段，总线格式开销为 55 B。握手消息体版本与外层 wire 版本不同。

2.1.4 ML-KEM-768：数学结构与接口语义

参数为 n = 256、q = 3329、k = 3，取 Rq = ℤq[X]/(X256 + 1)。公开矩阵 A 与短向量 s、误差 e 形成 t = As + e（mod q）；相应模格问题与 KEM 变换为标准机制提供安全依据。这里说明正确集成所需结构，完整算法以 FIPS 203 为准。[3][8][9]

因为 q−1 = 13×256，模 q 下可取 256 次单位根，而不存在 512 次本原单位根。ML-KEM 的 NTT 对应 128 个二次因子，将多项式乘法转换为 NTT 域运算；它属于上游标准库实现，不是团队新增算法。本节的数学结构说明不作为独立性能成果。[3]

算法1　ML-KEM-768 密钥生成与封装（标准流程说明）
Algorithm ML-KEM-768.KeyGen()  // k = 3, eta1 = 2
  1: d <- RandomBytes(32); z <- RandomBytes(32)
  2: (rho, sigma) <- G(d || byte(3))
  3: for i,j = 0,1,2: A_hat[i][j] <- SampleNTT(rho || byte(j) || byte(i))
  4: for i = 0,1,2: s[i] <- SamplePolyCBD_eta1(PRF_eta1(sigma, byte(i)))
  5: for i = 0,1,2: e[i] <- SamplePolyCBD_eta1(PRF_eta1(sigma, byte(i+3)))
  6: s_hat <- NTT(s); e_hat <- NTT(e)
  7: t_hat <- A_hat * s_hat + e_hat
  8: ek <- ByteEncode_12(t_hat) || rho                  // 1184 B
  9: dk <- ByteEncode_12(s_hat) || ek || H(ek) || z     // 2400 B
 10: return (ek, dk)

Algorithm ML-KEM-768.Encaps(ek)
  1: m <- RandomBytes(32); (K, r) <- G(m || H(ek))
  2: c <- K-PKE.Encrypt(ek, m, r)                     // 1088 B
  3: return (c, K)                                  // K: 32 B
算法2　ML-KEM-768 解封装与隐式拒绝（标准流程说明）
Algorithm ML-KEM-768.Decaps(dk, c)  // internal outline
  1: parse dk as encoded_s_hat || ek || h || z
  2: m_prime <- K-PKE.Decrypt(encoded_s_hat, c)
  3: (K_prime, r_prime) <- G(m_prime || h)
  4: c_prime <- K-PKE.Encrypt(ek, m_prime, r_prime)
  5: K_reject <- J(z || c)
  6: K_out <- constant_time_select(c == c_prime, K_prime, K_reject)
  7: return K_out

byte(i) 是单字节计数器，s 与 e 分别使用 0—2、3—5。等长非法密文通过 J(z ∥ c) 使用完整密文派生替代秘密；结构长度和输入合法性检查由对外接口另行处理。2,400 B 为标准扩展私钥编码长度，不是本项目尺寸测试序列化后的测量值。实际 ML-KEM-768 来自 Go crypto/mlkem，集成边界见 §2.1.10。

全部 Expand 标签带 edgehybrid/v1/ 前缀。Suite 1 的 IKM 只包括套件号、sm2 与 Zsm2，并拒绝不应出现的后量子共享输入。Finished 密钥不是 SM4 流量密钥，Finished 标签也不是直接截取的 KDF 输出。

D_A = H(E("edgehybrid/v1/t3core", m1, m2, ClientCore, SigA))
FinishedA = HMAC-SM3(kfinA, E("edgehybrid/v1/confirm-A", D_A))
D_B = H(E("edgehybrid/v1/t3", m1, m2, m3))
FinishedB = HMAC-SM3(kfinB, E("edgehybrid/v1/confirm-B", D_B))

身份签名输入分别为 E("edgehybrid/v1/server-auth", m1, ServerCore) 与 E("edgehybrid/v1/client-auth", m1, m2, ClientCore)。网关写出 m4 后，客户端核验 FinishedB 后，才按 T4 派生应用材料并接纳会话。认证、确认和派生输入不包含自身输出。

协商字段篡改可能首先触发结构、身份签名或 SM2 确认失败；到达 Finished 的路径再执行对应确认检查。E09 按实际拒绝位置计数，不用“哈希雪崩”替代安全论证。

2.1.8 双向记录保护与严格序号

Key / Nonce。两个方向分别使用 16 B SM4-GCM 密钥。Nonce = 4 B 方向前缀 ∥ 8 B Seq；前缀来自 T4 派生，Seq 在当前方向、Channel 和同一流量密钥内单调递增。Epoch 与 SID 在记录头中，不占 Nonce 位。[7][11]

AAD 与记录。33 B 记录头作为 AAD，绑定版本、套件、业务类型、方向、SID、Epoch 和 Seq；密文与 16 B 标签跟随其后。完整线格式见表1.5。

顺序与拒绝。接收端只接受 seq == next 的记录，并在 AEAD 核验成功后提交 next++。旧序号、跳跃和乱序返回错误，认证失败不提前推进状态；不采用位图滑动窗口。

手电筒作为控制生效后的可见提示，只对新的控制操作触发，不随每次温度上报闪烁。兼容时序为预关闭后等待 1 秒、开启 1 秒、关闭后等待 2 秒，单独工作线程串行执行，避免阻塞后续 ACK 与采集。同一操作的重试不重复触发；提示队列有界，异常单独记录。接口返回与物理亮灯分别验收，间隔 ACK 不代表对执行器状态的独立测量。

4.应用前景

4.1 本机业务闭环的三个实例

复现对象是同一 Windows 主机上的网关角色 GW001 与模拟设备 D001。以下步骤是操作说明；一次新运行是否成功，以该次运行保存的原始回执为准。已归档执行证据见 §3.5—3.6。

4.1.1 模拟温度上报与网关验收

  1. 建立连接。双击 runtime\启动交互平台.cmd，访问启动窗口打印的 PAGE_URL 并输入本次一次口令。在工作台选择 D001，打开指引，再点击“连接当前设备”，等待状态显示已认证在线，并核对实际通道模式。程序默认加载设备身份，加载本身不代表已连接。
  2. 发送一个确定的样本。如自动采样已开启，可先在“采样与会话设置”中暂停采样，便于辨认手动样本。在“发送温度”中输入 26.3 ℃，点击同名按钮。一次 HTTP 受理仅表示请求进入处理流程。
  3. 查看系统检查与结果。设备将温度和样本标识封装为受 SM4-GCM 保护的业务记录。网关完成记录验密后，重新检查当前可信准入、载荷中的设备身份、温度范围和样本顺序；通过后记录 telemetry_accepted。工作台应显示“网关已收到 26.3 ℃”，并能通过“查看详情与关联记录”定位同一运行、D001、会话和操作对应的记录。

温度 confirmed 来自网关验收，不表示额外遥测 ACK。手动输入不改变自动采样温度源。

4.1.2 设置上报间隔与设备状态 ACK

  1. 下发请求。保持 D001 在线，在“设置间隔”中选择“申请每 5 秒上报一次”，再点击“设置上报间隔”。此时分别保留申请值、已提交值和当前生效值。
  2. 核对处理链。设备验证控制操作标识和允许的间隔范围，完成本地调度器更新，再以实际生效状态生成受安全通道保护的 ACK。网关检查设备、SID、操作标识、Applied 及实际间隔是否与本次请求匹配，匹配后标记确认。
  3. 判断成功。工作台应显示“设备已设置 5 秒上报，网关已验证回执”，当前设备的上报间隔为 5 秒；关联记录中的操作标识与本次提交一致。若此前暂停了采样，间隔更新后仍保持暂停；需要观察周期上报时，再明确开启采样。

操作结果为 unconfirmed 时，设备可能已经执行，不应自动重复下发；会话内去重不等于跨重启严格一次执行。

4.1.3 完整会话换钥与新会话业务

  1. 提交明确换钥。保持四步指引开启，在“采样与会话设置”点击“完整会话换钥”，输入 rekey:D001 确认。记录此次请求对应的 rekey_id 和旧 SID。
  2. 核对新握手。等待指引将此次 rekey_id 关联到设备端完成的新握手和网关端准入，并观测到新旧 SID 不同。只看到请求已受理或 SID 变化时，仍不能把本步骤写成完成。
  3. 发送新会话样本。在换钥确认后手动发送 28.7 ℃。指引应显示本次换钥的双端准入已关联，且新 SID 上的验证消息已确认；关联记录必须属于本次运行和 D001。
  4. 保存复现材料。进入“证据总结”，先“锁定当前设备证据范围”，再“导出本次引导证据 JSON”，最后点击生成的下载链接保存文件。导出已生成与文件已保存分别记录。

临时会话更新与长期身份轮换不同。旧 Channel 关闭后重新握手，在新 SID 上继续业务，不恢复旧密钥。

5.1 三项核心成果

A：混合安全握手。完成基于标准原语的 SM2＋ML-KEM-768 四步握手，将可信身份、协商字段、SM2 确认和 Finished 组合为完整过程；用 T2/T4 将确认材料与应用材料分阶段派生。具体结构、状态和材料长度见 §2.1.6—2.1.7。

B：安全记录与业务因果确认。SM4-GCM、方向 Nonce 与严格 Seq 保护所接纳记录；queued→writing→written→confirmed 将通信动作与业务确认区分。温度验收和设备控制 ACK 采用不同证据判据，链式审计摘要明确所覆盖字段与可信根条件。

C：可复现的软件验证与证据体系。按 run_id、源码清单、程序身份和测试编号关联原始记录，分别展示历史性能、补测和复用证据。关键指标主值及批次见当前关键指标主表（表3.11），故障和恢复功能见 G01—G07，质量处置见 E08。本机 Web 工作台、多身份和批量操作是上述机制的工程载体。

本次结果体现从混合建钥、双向认证、记录保护、业务确认到证据导出的软件闭环；测试通过限定在对应输入和观察对象，证据复用与新增运行分别记账。

算法C.1　SM2 数字签名与验证说明
Algorithm SM2.Sign(dA, M, IDA):
  1:  ZA = SM3(ENTLA || IDA || a || b || xG || yG || xA || yA)
  2:  M_bar = ZA || M;  e = SM3(M_bar)
  3:  Loop:
  4:      k ← [1, n-1]; (x1, y1) = [k]G
  5:      r = (e + x1) mod n; If r == 0 or r + k == n Then Continue
  6:      s = ((1 + dA)^(-1) * (k - r * dA)) mod n; If s == 0 Then Continue
  7:      Return (r, s)

Algorithm SM2.Verify(PA, M, IDA, (r, s)):
  1:  If r, s not in [1, n-1] Then Return FAIL
  2:  ZA = SM3(ENTLA || IDA || a || b || xG || yG || xA || yA)
  3:  e = SM3(ZA || M);  t = (r + s) mod n;  If t == 0 Then Return FAIL
  4:  (x1', y1') = [s]G + [t]PA;  R = (e + x1') mod n
  5:  If R == r Then Return SUCCESS Else Return FAIL
算法C.2　SM3 的64轮压缩说明
Algorithm SM3.Compress(V_i, B_i):
  1:  消息字扩展: 对 512 位分组 B_i 划分为 16 个字 W_0~W_15
  2:  For j = 16 to 67: W_j = P1(W_{j-16} ^ W_{j-9} ^ (W_{j-3} <<< 15)) ^ (W_{j-13} <<< 7) ^ W_{j-6}
  3:  For j = 0 to 63: W'_j = W_j ^ W_{j+4}
  4:  (A, B, C, D, E, F, G, H) = V_i
  5:  For j = 0 to 63:
  6:      SS1 = ((A <<< 12) + E + (T_j <<< (j mod 32))) <<< 7
  7:      SS2 = SS1 ^ (A <<< 12)
  8:      TT1 = FF_j(A, B, C) + D + SS2 + W'_j
  9:      TT2 = GG_j(E, F, G) + H + SS1 + W_j
  10:     D = C; C = B <<< 9; B = A; A = TT1
  11:     H = G; G = F <<< 19; F = E; E = P0(TT2)
  12: Return V_i ^ (A, B, C, D, E, F, G, H)

-- 内层受保护记录头(33B): ver(1) | suite(2) | kind(1) | dir(1) | sid(16) | epoch(4) | seq(8)
local eh_proto = Proto("EdgeHybrid", "EdgeHybrid Post-Quantum Security Protocol")

local f_len   = ProtoField.uint32("eh.len",   "Frame Remaining Length", base.DEC)
local f_ver   = ProtoField.uint8 ("eh.ver",   "Frame Version", base.DEC)
local f_kind  = ProtoField.uint8 ("eh.kind",  "Message Kind", base.HEX)
local f_suite = ProtoField.uint16("eh.suite", "Cipher Suite", base.DEC)
local f_dir   = ProtoField.uint8 ("eh.dir",   "Direction", base.DEC)
local f_sid   = ProtoField.bytes ("eh.sid",   "Session ID")
local f_epoch = ProtoField.uint32("eh.epoch", "Epoch", base.DEC)
local f_seq   = ProtoField.uint64("eh.seq",   "Sequence (nonce low 64)", base.DEC)

eh_proto.fields = { f_len, f_ver, f_kind, f_suite, f_dir, f_sid, f_epoch, f_seq }

function eh_proto.dissector(buffer, pinfo, tree)
    if buffer:len() < 6 then return end
    local rem = buffer(0,4):uint()
    if rem ~= buffer:len() - 4 then return end          -- 长度自洽才认为是本协议
    pinfo.cols.protocol = "EdgeHybrid"
    local st = tree:add(eh_proto, buffer(), "EdgeHybrid Frame")
    st:add(f_len,  buffer(0,4))
    st:add(f_ver,  buffer(4,1))
    local kind = buffer(5,1):uint()
    st:add(f_kind, buffer(5,1))
    if kind == 16 and buffer:len() >= 6 + 33 then         -- ProtectedRecord
        local off = 6
        st:add(f_suite, buffer(off+1,2))
        st:add(f_dir,   buffer(off+4,1))
        st:add(f_sid,   buffer(off+5,16))
        st:add(f_epoch, buffer(off+21,4))
        st:add(f_seq,   buffer(off+25,8))
    end
end
