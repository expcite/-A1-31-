# 核心设计冻结约定

## 目标
本轮是R5性能、R6交付和可审计创新的最终范围整理，不再以“优化”为名新增核心能力。核心冻结不构成无漏洞证明、安全认证或跨平台全覆盖。

## 冻结对象

|对象|固定内容|
|---|---|
|密码与套件|现有传统Suite1、SM2+ML-KEM混合Suite2；SM3派生和SM4认证加密；长期签名/协商密钥分开|
|握手与记录|H1—H4、身份/模式/转录绑定、Finished、线路编码、nonce/seq、方向密钥分离、防重放、防降级|
|会话及管理|每连接受控接收、发送串行、按SID绑定操作、本机可信注册表与CAS、网关维护窗口、旧任务与会话结束语义|
|产品定位|Windows本机软件原型/模拟设备、命令行和当前图形入口；非远程PKI、非工业安全认证|
|架构|保留现有模块与接口分层；不改语言/前端框架，不增加数据库或分布式基础设施|
|证据原则|真实退出码、失败保留、未知null+原因、历史来源不变、当前结果不冒充旧结果/反之|

## 完成后仍允许的修改
1. 可复现的bug修复：给出原反例、正常对照、修后同例；最小影响分析及实际回归。
2. 用户另行指定的前端设计/易用性完善：不得暗中改变权限、成功含义或真实通道路径。
3. 路径、说明、依赖披露和证据整理：不得修改历史实验事实。

## 需要另行授权的改变
新套件、协议编码/KDF改变、0-RTT、恢复票据、远程管理、多租户、聊天/文件、数据库重构、标准S1/S2进主协议、后量子身份签名等，均作为独立版本需求，不能顺手实施。

若发现严重核心安全bug，不能用“已冻结”阻止修复。应记录影响、临时限制、新版本/协议标识与最小回归；需要协议破坏性变化时先说明并授权，不静默更换设计。

## 冻结凭证
最终写入实际文件：版本、H_input源码/计划清单、原构建命令与EXEhash、前端hash、当前/历史证据索引、开放bug与未测范围、完成验收回执。H_delivery用于最终打包，不等于测量H_input。
无新运行证据时，冻结状态只能记READY_FOR_LOCAL_VALIDATION，而不是CORE_VALIDATED。

本文件是冻结前输入约定。实际H_input/H_delivery及G01—G12状态写外置回执；无结果时NOT_EXECUTED，不能在源码中预写CORE_VALIDATED。
